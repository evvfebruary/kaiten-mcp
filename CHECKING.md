# Проверка совместимости Kaiten MCP

Из корня репозитория после `uv sync --locked --group dev`:

```bash
uv run kaiten-mcp-check offline
uv run kaiten-mcp-check docs
uv run kaiten-mcp-check live
uv run kaiten-mcp-check all
```

`offline` запускает все автономные pytest-проверки, включая каждый из 15 инструментов
через MCP-клиент и настоящие процессы stdio/HTTP с локальным тестовым API.
Обычный `uv run pytest` также исключает live-тесты; `uv run pytest -m live` включает их явно.
Явный live-запуск без настроек завершается ошибкой, а не пропуском.

`docs` сравнивает страницы официальной документации используемых методов и каталог
API с `checks/kaiten-docs.json`. Новые неиспользуемые методы информационны. Любое
изменение используемой страницы требует просмотра, даже если оно обратно совместимо:
это детектор изменений документации, а не доказательство поломки API. Неисправный
парсер или недоступный сайт дают `source_error`. Автоматическое сравнение не меняет эталон.

После просмотра `reports/docs.diff` и `reports/docs-current.json` принять обновление:

```bash
uv run kaiten-mcp-check docs --update-baseline
```

Команда заново загружает страницы. Проверить итоговый git diff перед коммитом.
Для изменения MCP-контрактов отдельно обновить `tests/checks/tool_schemas.json` после
проверки совместимости: снимок содержит полные схемы `create_server().list_tools()`,
сериализованные через `model_dump(mode="json", by_alias=True, exclude_none=True)`.
Новый инструмент должен также появиться в реестре и в live-сценарии.

## Облачный стенд

Нужны выделенная доска в тестовом пространстве, две разные колонки, одна дорожка,
заранее созданный тег и токен с правами на чтение, создание, изменение и удаление
тестовых карточек. Экспортировать переменные из `.env.example`; CLI проверок читает
токен и идентификаторы именно из окружения, а не автоматически из `.env`.

- `KAITEN_API_TOKEN`
- `KAITEN_WORKSPACE_SLUG` или `KAITEN_BASE_URL` (не задавать пустой BASE_URL)
- `KAITEN_TEST_SPACE_ID`, `KAITEN_TEST_BOARD_ID`
- `KAITEN_TEST_COLUMN_ID`, `KAITEN_TEST_TARGET_COLUMN_ID`, `KAITEN_TEST_LANE_ID`
- `KAITEN_TEST_TAG_ID`, `KAITEN_TEST_TAG_NAME`

Каждый запуск создаёт карточку `mcp-check-<uuid>`, проверяет изменения последующим
чтением и удаляет только созданную им карточку в `finally`. Тег берётся существующий.
Ошибка очистки сохраняет `card_id` в отчёте для ручной уборки. Принудительное завершение
процесса или потеря ответа на создание могут оставить карточку: искать по `run_id`
и префиксу названия. Автоматического удаления по одному префиксу нет.

Локальные процессы на одной машине блокируются по адресу API и ID доски. GitHub
Actions сериализует запуски workflow. Между разными машинами общей блокировки нет:
для параллельной локальной работы использовать отдельную доску.

## CI и отчёты

PR запускает автономные проверки, Ruff, ty, бюджеты ответов и сборку пакета.
`Kaiten compatibility` запускается ежедневно в 06:00 UTC и вручную. Для live-job
создать GitHub Environment `kaiten-test`: токен положить в Secret `KAITEN_API_TOKEN`,
остальные переменные — в Environment Variables с теми же именами. Без настройки
job будет красным с `not_configured`. Workflow начнёт работать после попадания
в основную ветку; локальные файлы сами по себе не включают расписание GitHub.

По умолчанию результаты пишутся в игнорируемый git каталог `reports/`; можно
переопределить через `--output`. JSON различает `passed`, `failed`, `skipped`,
`not_configured`, `source_error`, `docs_changed`. Есть Markdown summary, JUnit и diff
документации. В Actions артефакты хранятся 14 дней. Live-отчёт содержит статусы,
тип ошибки, run ID и ID карточки для очистки; тела ответов и токены не записываются.
Проверки документации и настоящего Kaiten выполняются независимо.

Dependabot еженедельно предлагает обновления Python-зависимостей и Actions.
Major SDK ограничен `<3`; обновления проходят те же контрактные и транспортные тесты.

## Изменения при миграции

- Python SDK обновлён с 1.28.1 до 2.3.0; используется `MCPServer` и новые настройки транспорта.
- Проверяются протоколы 2026-07-28 и legacy 2025-11-25 на stdio и Streamable HTTP.
- Имена инструментов и компактные поля сохранены; добавлены конкретные схемы результатов,
  аннотации операций, стабильный порядок инструментов и структурированные ошибки.
- HTTP-запрос без своего Bearer-токена больше не использует серверный `KAITEN_API_TOKEN`.
  Существующий режим ручного токена не является реализацией MCP OAuth; OAuth отложен.
- GET `/spaces` и GET `/cards/{id}/comments` читаются постранично: с 1 октября 2026
  Kaiten ограничивает страницу сотней элементов. Неправильные элементы списка больше
  не отбрасываются молча. При более чем 1000 страницах возвращается ошибка.
- Неоднозначные сетевые ошибки и 5xx не вызывают автоматический повтор записи.
  429 допускает ограниченный повтор после ожидания.

Основания: [миграция SDK](https://py.sdk.modelcontextprotocol.io/migration/),
[изменения MCP](https://modelcontextprotocol.io/specification/2026-07-28/changelog),
[авторизация MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization),
[пространства Kaiten](https://developers.kaiten.ru/spaces/retrieve-list-of-spaces),
[комментарии Kaiten](https://developers.kaiten.ru/card-comments/retrieve-card-comments).
Локальная установка настоящего Kaiten требует доступа к серверной версии от вендора;
для этого проекта выбран выделенный облачный стенд.

## Воспроизводимый демо-стенд

`scripts/prepare_demo.py` предназначен только для `evvbmstu.kaiten.ru`, пространства
`Main` (937553). Он напрямую вызывает REST API для создания структуры, не добавляя
административных инструментов в MCP. Адрес проверяется до отправки токена;
HTTP-перенаправления отключены.

Из корня репозитория загрузите локальный файл с токеном (в Git его нет):

```bash
set -a
source "$HOME/.config/kaiten-mcp/demo.env"
set +a
uv run python scripts/prepare_demo.py          # только просмотр, без записей в Kaiten
uv run python scripts/prepare_demo.py --apply  # создать недостающие данные
```

| Доска | Данные | Назначение |
|---|---|---|
| MCP Demo | 6 карточек на английском | Обзор доски, демонстрация в Cursor |
| MCP Scenarios | 25 карточек | Пагинация, неоднозначный поиск, пустые/длинные описания, сроки |
| MCP Integration | Нет постоянных карточек | Изолированный жизненный цикл live-тестов |

Везде три колонки `To Do`, `In Progress`, `Done` и стандартная дорожка.
Начальные даты рассчитываются относительно первого создания карточки; повторный запуск
не сдвигает сроки. Начальные карточки имеют комментарии и теги, а две карточки сценариев —
одинаковый заголовок. Длинное описание позволяет проверить явное усечение ответа MCP.
Все данные вымышленные, исполнители не назначаются. Тег `mcp-test` постоянно прикреплён
к первой карточке `MCP Demo`: Kaiten не возвращает неиспользуемые теги в списке,
поэтому такая привязка сохраняет его видимость для preflight live-тестов.
Удаление этой привязки приводит к остановке подготовки, а не к её молчаливому восстановлению.

Скрипт сопоставляет доски и карточки по стабильному `external_id`. Ручные правки,
перемещения и снятие добавленных скриптом тегов сохраняются. Недостающие объекты
добавляются, но ранее созданный объект, который удалили или лишили идентификатора,
вызывает остановку вместо автоматического восстановления. Изменённая структура колонок
или дорожек требует ручного разбора. Совпадение названия с чужой доской/карточкой
также останавливает соответствующую операцию.

Результаты (все файлы игнорируются Git):

- `reports/demo-fixture.json` — ID и ссылки на доски и карточки, действия последнего запуска.
- `reports/demo-test.env` — настройки `KAITEN_TEST_*`, без токена.
- `reports/demo-fixture-state.json` — журнал подтверждённых записей и незавершённой операции.

Сохраняйте журнал между запусками. Скрипт не удаляет и не сбрасывает стенд.
Не запускайте подготовку одновременно с разных машин; локальные процессы защищены
общей блокировкой в `~/.config/kaiten-mcp/demo-fixture.lock`.

После ошибки записи или прерывания `pending` в журнале блокирует новый запуск.
Проверьте указанный объект по `external_id` (для комментария — по маркеру в тексте,
для тега — по имени). Если запись состоялась, внесите её ID в `done` под ключом
из `pending`; если достоверно не состоялась — повтор возможен после удаления `pending`.
При неопределённом результате оставьте блокировку. Тела HTTP-ошибок и токены скрипт не выводит.

Автоматические проверки на отдельной доске:

```bash
source reports/demo-test.env
uv run kaiten-mcp-check live --output reports/demo-live
```

Live-проверка создаёт одну временную карточку и удаляет только её. Постоянные карточки
на двух остальных досках остаются для ручных сценариев и [записи GIF](docs/demo.md).
Для ручного поиска проверяйте две карточки `Kaiten scenario: Review login flow`;
полный список `MCP Scenarios` должен потребовать две страницы при стандартном лимите 20.

Проверки самого скрипта без доступа к Kaiten:

```bash
uv run pytest tests/checks/test_demo_fixture.py
```
